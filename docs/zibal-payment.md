# پرداخت زیبال در MiniKandoo

این راهنما رفتار نسخهٔ فعلی را توضیح می‌دهد. اصلاح قبلی پذیرش شمارهٔ مرجع رشته‌ای در commit `910c231f64e2c78677b21699c096e70bbf8756ec` حفظ شده است. راهنمای عملیات در [بازیابی تراکنش‌ها](zibal-verification-recovery.md) و [بکاپ دیتابیس](production-database-backups.md) قرار دارد. پیاده‌سازی و آزمون محلی، اثبات استقرار یا صحت تراکنش‌های واقعی نیست.

## قرارداد و اعتبارسنجی

چرخهٔ عادی IPG، callback از نوع GET و APIهای JSON روی HTTPS استفاده می‌شوند:

| عملیات | نشانی | نتیجه |
| --- | --- | --- |
| درخواست | `POST https://gateway.zibal.ir/v1/request` | `result=100` فقط ایجاد جلسهٔ پرداخت است |
| ورود مشتری | `https://gateway.zibal.ir/start/{trackId}` | Referer دامنهٔ فروشگاه ارسال می‌شود |
| تأیید | `POST https://gateway.zibal.ir/v1/verify` | `100` نیازمند اطلاعات منطبق و `status=1` است |
| استعلام | `POST https://gateway.zibal.ir/v1/inquiry` | برای بررسی مستقل و بازیابی استفاده می‌شود |

مبلغ از `Order.total` در سرور گرفته می‌شود. ذخیره‌سازی به تومان باقی می‌ماند و adapter برای زیبال آن را در ۱۰ ضرب می‌کند. مبلغ، شمارهٔ سفارش، شناسهٔ تراکنش در صورت وجود در پاسخ، وضعیت و شمارهٔ مرجع تطبیق داده می‌شوند. `trackId` عدد مثبت int64 است و در `Payment.authority` به شکل رشتهٔ یکتا ذخیره می‌شود.

`refNumber` یکی از این دو شکل را می‌پذیرد:

- integer مثبت با نمایش حداکثر ۶۴ رقم؛ boolean، حتی `True`، integer معتبر نیست.
- رشتهٔ ۱ تا ۶۴ رقم ASCII مطابق `[0-9]{1,64}` با مقدار مثبت؛ صفرهای ابتدایی عیناً حفظ می‌شوند.

صفر، مقدار منفی، float، علامت مثبت، فاصله، newline، نقطهٔ اعشار، object، رقم فارسی/عربی و مقادیر طولانی رد می‌شوند. دادهٔ خراب به شمارهٔ معتبر تبدیل نمی‌شود. **۶۴ حد موجود `Payment.reference_id` در پروژه است؛ OpenAPI زیبال حداکثر طولی برای `refNumber` اعلام نکرده است.** توصیف رسمی integer است، اما گزارش حادثه نشان داده که پاسخ واقعی می‌تواند numeric string باشد.

پارامترهای callback شامل `trackId`، `success`، `status` و `orderId`، بدون تکرار و با مقدار معتبر، لازم‌اند. تراکنش از شناسهٔ ذخیره‌شده و `gateway=zibal` پیدا می‌شود. `success=1` در URL اثبات پرداخت نیست. پاسخ Verify با کد `201` فقط با Inquiry معتبر پذیرفته می‌شود؛ `202` نیز نیازمند Inquiry است. تغییر به وضعیت پرداخت‌شده بین Verify و Inquiry، خطای قابل تکرار است. خطای شبکه، HTTP، JSON یا اطلاعات مالی، سفارش را موفق نمی‌کند.

## شاهد رسمی دربارهٔ paidAt و timezone

منابع بررسی‌شده در ۲۰۲۶-۱۱-۱۵:

- [راهنمای رسمی IPG](https://help.zibal.ir/ipg/)
- [OpenAPI رسمی](https://api.zibal.ir/static/helpdocs/ipg.json)، OpenAPI `3.1.1`، نسخهٔ `1.0.0`
- SHA256 فایل بررسی‌شده: `0231758f40572777e98b12107926363dcf84a9af120c5485b5e3209a9a31a3e2`

در schema پاسخ `/v1/verify` و `/v1/inquiry`، `paidAt` رشته، `format=date-time` و توضیح «به فرمت ISODate» دارد. مثال‌های رسمی `2018-03-25T23:43:01.053000` و `2022-07-06T14:18:21.742000` فاقد offset هستند. مستند timezone این مثال‌ها، UTC یا `Asia/Tehran` را مشخص نمی‌کند. مالک پروژه نیز تأیید کتبی timezone در اختیار ندارد. بنابراین قالب رسمی به‌تنهایی مجوز فرض‌کردن timezone نیست.

`payments/gateways/zibal_time.py` زمان را مستقل تفسیر می‌کند:

| ورودی | تفسیر |
| --- | --- |
| ISO با `Z` یا offset معتبر مثل `+03:30` | با همان offset به UTC تبدیل می‌شود؛ تنظیم محلی آن را جایگزین نمی‌کند |
| ISO بدون offset و تنظیم خالی | `manual_review` با دلیل `timezone_unconfirmed`؛ بدون fulfillment یا تصمیم خودکار refund |
| ISO بدون offset و IANA رسماً تأییدشده | با `ZIBAL_PAID_AT_TIMEZONE` تفسیر و به UTC تبدیل می‌شود |
| timezone نامعتبر، DST fold یا gap | بررسی دستی؛ یک ساعت احتمالی به‌طور دلخواه انتخاب نمی‌شود |
| `-00:00` | offset نامعلوم RFC3339؛ بررسی دستی |
| تاریخ نامعتبر، بیش از ۶ رقم اعشار، offset مثل `+03:60`، زمان خارج از محدودهٔ ذخیره‌سازی | بررسی دستی؛ داده اصلاح یا کوتاه نمی‌شود |
| زمان آینده نسبت به مشاهدهٔ فعلی | بررسی دستی؛ رسیدن ساعت به آن زمان موجب پذیرش خودکار در retry نمی‌شود |

به‌صورت پیش‌فرض:

```env
ZIBAL_PAID_AT_TIMEZONE=
```

پس از تأیید کتبی زیبال، نام IANA تأییدشده را در محیط خصوصی ثبت و منبع و تاریخ تأیید را در پروندهٔ عملیات نگه دارید. تغییر تنظیم کافی است؛ منطق اصلی بازنویسی نمی‌شود. این راهنما مقدار timezone پیشنهادی ندارد. گزینهٔ `--gateway-timezone` در ابزار بازیابی نیز فقط برای همین تأیید رسمی است.

## معنای زمان‌های ذخیره‌شده

| فیلد | معنا |
| --- | --- |
| `Payment.gateway_paid_at` | زمان واقعی گزارش‌شده توسط درگاه، پس از تفسیر قابل اتکا؛ nullable است |
| `Payment.paid_at` | زمان محلی اولین ثبت موفق دریافت وجه؛ در retry بازنویسی نمی‌شود |
| `Payment.verified_at` | زمان محلی بررسی سروری |
| `Order.paid_at` | زمان محلی پذیرش پرداخت برای سفارش |

مقایسه با `Order.expires_at` بر اساس `gateway_paid_at` است. زمان ورود callback، زمان پرداخت مشتری محسوب نمی‌شود. raw `paidAt` در `metadata.verification.paidAt` و پاسخ‌های متفاوت در `verification_history` حفظ می‌شوند؛ تفسیر در `payment_time` و تصمیم در `decision` قرار دارد. زمان آیندهٔ قابل parse نیز برای ممیزی ذخیره می‌شود، اما وضعیت پرداخت همچنان manual review است. برای legacy records، زمان درگاه از زمان‌های محلی یا مثال مستندات ساخته نمی‌شود.

## مهلت، موجودی و پرداخت اضافه

| وضعیت | رفتار |
| --- | --- |
| پرداخت ۱۰:۲۸، مهلت ۱۰:۳۰، callback ۱۰:۳۵؛ سفارش فعال و رزرو سالم | پرداخت پذیرفته می‌شود؛ رسیدن دیرهنگام callback مانع نیست |
| زمان واقعی پرداخت پس از مهلت | دریافت موفق وجه ثبت، `needs_refund=True`؛ سفارش پرداخت‌شده نمی‌شود؛ job انقضا وضعیت و آزادسازی را انجام می‌دهد |
| job انقضا قبلاً لغو و موجودی را آزاد کرده است | سفارش احیا و موجودی دوباره رزرو نمی‌شود، حتی با زمان زودهنگام معتبر؛ رسید برای refund handling ثبت می‌شود |
| سفارش قبلاً با تراکنش دیگر پرداخت شده | رسید دوم حفظ و refund flag می‌گیرد؛ fulfillment دوباره انجام نمی‌شود |
| timestamp مبهم یا نامعتبر | `manual_review` مستقل؛ بدون fulfillment یا فرض دیرکرد/refund، حتی روی سفارش لغوشده یا پرداخت‌شده |
| سفارش فعال ولی آیتم/واریانت رزرو مفقود است | بررسی دستی و حفظ رسید؛ موجودی اختراع نمی‌شود |

زمان دقیقاً برابر مهلت، داخل مهلت محسوب می‌شود. `Order.inventory_released` آزادسازی رزرو را ثبت می‌کند. آزادسازی تنها یک بار، در مسیر لغو/انقضا، تحت قفل انجام می‌شود. ایجاد سفارش موجودی را رزرو می‌کند؛ callback موجودی را دوباره کاهش نمی‌دهد. وضعیت‌های ناموفق بعدی نمی‌توانند سفارش پرداخت‌شده را تنزل دهند.

اگر رسید موفق دیگری برای همان سفارش `MANUAL_REVIEW` باشد، callback معتبر تازه نیز با دلیل `another_receipt_requires_review` در بررسی دستی ثبت می‌شود؛ زمان قابل‌فهم آن، رسید قبلی را کنار نمی‌زند. شناسه‌ها، raw `paidAt` و تاریخچهٔ Verify حفظ و `needs_refund=False` می‌ماند. پس از paid شدن معتبر سفارش، رفتار پرداخت اضافه و کنترل سفارش لغوشده/رزرو آزادشده همچنان برقرار است.

سفارش دارای رسید بررسی دستی، حتی پس از مهلت، خودکار منقضی نمی‌شود. query اولیه آن را حذف می‌کند و job پس از قفل سفارش دوباره وجود رسید دستی را بررسی می‌کند. رزرو صرفاً نگه داشته می‌شود و سفارش paid نمی‌شود. این موجودی ممکن است تا حل پرونده اشغال بماند؛ پشتیبانی باید سریع بررسی کند. ادمین سفارش تعداد «رسیدهای نیازمند بررسی دستی» را با annotation خواندنی نشان می‌دهد و Payment Admin فیلتر وضعیت را حفظ می‌کند. پس از رفع رسید دستی و در صورت unpaid بودن سفارش، قواعد انقضای عادی دوباره اعمال می‌شوند.

manual review در پنل مدیریت با فیلتر وضعیت و نمایش زمان درگاه/metadata قابل بررسی است. کاربر پیام مراجعه به پشتیبانی می‌بیند و ایجاد پرداخت تازه برای همان سفارش مسدود می‌شود. `needs_refund=True` صرفاً نیاز به بررسی بازگشت وجه است؛ هیچ refund خودکاری وجود ندارد. تأیید انسانی موارد مبهم باید با ممیزی انجام شود؛ تغییر مستقیم status یا حذف رسید راه حل نیست.

## قفل و ایدمپوتنسی

callback دو مرحله دارد: ابتدا snapshot لازم و هویت callback خوانده و HTTP Verify/Inquiry بدون `transaction.atomic` یا قفل ردیف انجام می‌شود. سپس یک تراکنش کوتاه با ترتیب `Order → Payment → ProductVariant` وضعیت تازه را می‌خواند و idempotency، هویت، primary دیگر، رسیدهای دستی، زمان و موجودی را دوباره بررسی می‌کند. caller نباید سرویس را در یک تراکنش بیرونیِ شامل HTTP قرار دهد؛ view و فرمان recovery مستقیم فراخوانی می‌کنند. لغو/انقضا `Order → ProductVariant` و واریانت‌ها ascending PK را قفل می‌کنند.

مجوز داخلی recovery فقط برای primary مشخص، پس از Inquiry کامل همهٔ رسیدهای بالقوه موفق، زمان‌ها و referenceهای معتبر، انتخاب primary یکتا و بکاپ تازهٔ معتبر صادر می‌شود. boolean یا پارامتر callback نمی‌تواند این مجوز را فعال کند. مجوز به fingerprint کل تاریخچه، شواهد و plan ثبت‌شده در audit متصل است؛ تغییر تاریخچه یا timestamp/reference هنگام HTTP، آن را بی‌اعتبار می‌کند. این مجوز فقط مانع «رسید دستی دیگر» را برای همان primaryِ بررسی‌شده رفع می‌کند؛ cancellation، inventory release، deadline، future time، هویت و قفل‌ها همچنان کنترل می‌شوند.

اگر callback اول قفل سفارش را بگیرد و پرداخت معتبر را بپذیرد، job انقضا پس از گرفتن قفل، paid بودن را دوباره بررسی و از لغو صرف‌نظر می‌کند. اگر انقضا اول قفل بگیرد، لغو و آزادسازی commit می‌شوند و callback بعدی صرفاً رسید و refund/review را ثبت می‌کند. callback پس از موفقیت نهایی، Verify تازه نمی‌زند. دو callback هم‌زمانِ هنوز نهایی‌نشده ممکن است هر دو Verify/Inquiry کنند؛ ثبت نهایی و fulfillment فقط یک بار است و درخواست دیرتر دادهٔ قطعی را بازنویسی نمی‌کند. تلاش‌های مختلف زیر قفل مشترک سفارش فقط یک primary می‌سازند. گذار ادمین به `paid` بدون وضعیت مالی موفق رد می‌شود.

## migration و تنظیمات

دو migration افزایشی نسخهٔ پایه لازم‌اند؛ اصلاحات هدفمند فعلی migration تازه‌ای ندارند:

```text
orders/0002_order_inventory_released_alter_order_payment_status
payments/0003_payment_gateway_paid_at_alter_payment_needs_refund_and_more
```

اولی سفارش‌های legacy لغوشده را به‌صورت محافظه‌کارانه `inventory_released=True` علامت می‌زند؛ هیچ stock یا وضعیت سفارش تغییر نمی‌کند. دومی فیلد nullable درگاه و choice بررسی دستی را اضافه می‌کند. زمان‌های محلی، مبلغ و reference قبلی حفظ می‌شوند. forward/backward در دیتابیس‌های جداگانه آزمایش شده‌اند. برگشت schema پس از ایجاد سوابق جدید manual review به بررسی جداگانه نیاز دارد؛ migration عقب، ابزار بازیابی داده نیست.

تنظیمات اصلی:

```env
PAYMENT_GATEWAY=zibal
ZIBAL_MERCHANT=
ZIBAL_TIMEOUT_SECONDS=10
ZIBAL_PAID_AT_TIMEZONE=
SITE_URL=https://minikandoo.ir
```

merchant واقعی فقط در محیط خصوصی قرار می‌گیرد؛ حساب تست `zibal` در production ممنوع است. endpoint، Referer، URLconf، تبدیل تومان/ریال و سوابق درگاه‌های تاریخی حفظ شده‌اند. whitelist ممیزی شامل داده‌های لازم پرداخت است؛ کارت، merchant، پیام دلخواه gateway و credential در گزارش‌ها ثبت نمی‌شوند.

## تکرار آزمون محلی

```sh
PYTHONPATH=scripts/qa .venv/bin/python manage.py test --settings=shop_test_settings --noinput
PYTHONPATH=scripts/qa .venv/bin/python manage.py makemigrations --check --dry-run --settings=shop_test_settings
.venv/bin/python scripts/qa/test_backup_stack.py
```

دستور آخر کل suite را روی MariaDB جداگانه اجرا و backup image را می‌سازد؛ concurrency، migration و restore را نیز بررسی می‌کند. پاسخ‌های زیبال شبیه‌سازی‌اند. هیچ تست با production settings یا دیتابیس فروشگاه اجرا نشود. روش آزمون و حدود اعتبار در [راهنمای بازیابی](zibal-verification-recovery.md) و نتایج واقعی در گزارش تحویل ثبت می‌شوند.
