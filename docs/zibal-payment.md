# اتصال و گزارش مهاجرت پرداخت زیبال

زیبال تنها درگاه فعال MiniKandoo است. در نسخهٔ بررسی‌شده، اتصال اجرایی درگاه قبلی وجود نداشت و پرداخت با شبیه‌ساز توسعه انجام می‌شد؛ مثال‌ها و تنظیمات قدیمی حذف و چرخهٔ کامل زیبال روی همان رابط پرداخت پیاده‌سازی شد.

مدل‌های دیتابیس، سوابق مالی، ایجاد سفارش، رزرو موجودی، سبد خرید، حساب کاربری، قیمت‌گذاری، ارسال، پنل مدیریت و طراحی صفحات تغییر نکرده‌اند. تغییرات خارج از ماژول پرداخت به تنظیمات موردنیاز، ویژگی‌های غیرظاهری صفحهٔ انتقال، مستندات و آزمون‌های پرداخت محدودند.

این متن گزارش مهاجرت اولیه است. اصلاح اعتبارسنجی `refNumber`، بررسی مهلت سفارش و ابزار بازیابی بعدی در [گزارش حادثه و راهنمای بازیابی](zibal-verification-recovery.md) ثبت شده‌اند. استقرار و بازیابی واقعی این اصلاح طبق درخواست مالک پروژه بر عهدهٔ او است.

## منبع رسمی

پیش از پیاده‌سازی، تمام محتوای [مستندات IPG زیبال](https://help.zibal.ir/ipg/) شامل مثال‌ها، جداول وضعیت و نتیجه، متدهای عادی و Lazy بررسی شد. صفحهٔ رسمی محتوای API را با Scalar از [فایل رسمی OpenAPI](https://api.zibal.ir/static/helpdocs/ipg.json) بارگذاری می‌کند؛ همان فایل کامل دریافت و مطالعه شد. [راهنمای رسمی Referer](https://help.zibal.ir/article/why-referrer-header-is-required) نیز بررسی شد.

پیاده‌سازی از چرخهٔ عادی `v1` استفاده می‌کند که callback آن `GET` است. روش Lazy و callback نوع `POST` فعال نشده‌اند.

## API و نگاشت به ساختار موجود

تمام درخواست‌های API به صورت JSON و از طریق HTTPS ارسال می‌شوند. احراز هویت با فیلد `merchant` در بدنهٔ درخواست است؛ این API به کلید یا هدر احراز هویت دیگری در این چرخه نیاز ندارد.

| عملیات | روش و نشانی | ورودی مورد استفاده | نتیجهٔ مورد انتظار |
| --- | --- | --- | --- |
| ایجاد پرداخت | `POST https://gateway.zibal.ir/v1/request` | `merchant`، `amount` ریالی، `callbackUrl`؛ همچنین `orderId`، `description` و `mobile` | `result=100` و `trackId` معتبر |
| ورود مشتری به درگاه | `GET https://gateway.zibal.ir/start/{trackId}` | شناسهٔ دریافت‌شده در مسیر URL؛ هدر `Referer` دامنهٔ فروشگاه | صفحهٔ میزبانی‌شدهٔ پرداخت |
| تایید پرداخت | `POST https://gateway.zibal.ir/v1/verify` | `merchant` و `trackId` عددی | `result=100`، `status=1` و اطلاعات مالی منطبق |
| استعلام برای بازیابی یا تعیین وضعیت | `POST https://gateway.zibal.ir/v1/inquiry` | `merchant` و `trackId` عددی | `result=100` و وضعیت/اطلاعات همان تراکنش |

فیلدهای ضروری درخواست طبق مستندات `merchant`، `amount` و `callbackUrl` هستند. پروژه همیشه `orderId` را هم می‌فرستد تا اتصال تراکنش به سفارش در callback و پاسخ سرور کنترل شود.

| دادهٔ زیبال | محل و رفتار در پروژه |
| --- | --- |
| `trackId` | به صورت رشته در فیلد یکتای موجود `Payment.authority`؛ در درخواست تایید/استعلام به صورت عدد int64 |
| `orderId` | همان `Order.order_number`؛ سفارش از رابطهٔ موجود `Payment.order` شناسایی می‌شود |
| `amount` | دیتابیس به تومان باقی می‌ماند؛ فقط adapter برای ارسال و تطبیق، مبلغ را در ۱۰ ضرب می‌کند |
| `refNumber` | عدد صحیح مثبت یا رشتهٔ ۱ تا ۶۴ رقم ASCII با مقدار مثبت؛ به صورت رشته در `Payment.reference_id` ذخیره و صفرهای ابتدایی رشته حفظ می‌شوند |
| شناسهٔ تراکنش داخلی پرداخت | `Payment.transaction_id` همان `trackId` تاییدشده را نگه می‌دارد |

برای مثال، سفارش ۵۵۰٬۰۰۰ تومانی با مبلغ ۵٬۵۰۰٬۰۰۰ ریال به زیبال ارسال می‌شود. حداقل رسمی ۱٬۰۰۰ ریال و سقف عمومی ۴٬۰۰۰٬۰۰۰٬۰۰۰ ریال بررسی می‌شود؛ زیبال ممکن است برای پذیرنده سقف کمتری تعیین کرده باشد. محاسبه از مبلغ سفارش در سرور انجام می‌شود و مبلغ یا میزبان ارسالی مشتری ملاک نیست.

نام فیلد `authority` برای حفظ سازگاری دیتابیس و سوابق قبلی تغییر نکرده است. هیچ migration یا تبدیل مبلغ در رکوردهای تاریخی لازم نیست.

## بازگشت و تایید امن

URL موجود `/payments/callback/` چهار پارامتر `trackId`، `success`، `status` و `orderId` را با `GET` دریافت می‌کند. در مستندات، `orderId` در صورت ارسال هنگام درخواست برمی‌گردد؛ چون پروژه همیشه آن را می‌فرستد، بازگشت آن در این پیاده‌سازی الزامی است.

پارامترهای ناقص، تکراری، شناسهٔ غیرعددی/خارج از int64، وضعیت ناشناخته یا سفارش نامنطبق رد می‌شوند. ابتدا پرداخت با `gateway=zibal` و شناسهٔ ذخیره‌شده پیدا می‌شود؛ `orderId` به‌تنهایی برای یافتن یا تغییر سفارش استفاده نمی‌شود. سوابق درگاه‌های پیشین حفظ و نمایش داده می‌شوند، اما callback زیبال آن‌ها را پردازش نمی‌کند.

`success` و `status` در URL دلیل پرداخت نیستند. برای callback معتبر، تایید سروری حتی در صورت اعلام شکست یا انصراف انجام می‌شود. موفقیت فقط با وضعیت تاییدشدهٔ سرور، مبلغ ریالی منطبق، شناسهٔ سفارش منطبق، شمارهٔ مرجع معتبر و زمان پرداخت ISO معتبر پذیرفته می‌شود. اگر پاسخ سرور شناسهٔ تراکنش را نیز برگرداند، آن شناسه هم تطبیق داده می‌شود.

| کد یا وضعیت رسمی | رفتار |
| --- | --- |
| نتیجهٔ درخواست `100` | فقط جلسهٔ پرداخت ساخته شده است؛ سفارش هنوز پرداخت‌شده نیست |
| نتیجهٔ تایید `100` و وضعیت `1` | پس از تطبیق اطلاعات، پرداخت و سفارش موفق ثبت می‌شوند |
| نتیجهٔ تایید `201` | قبلاً تایید شده؛ موفقیت فقط پس از استعلام با وضعیت `1` و اطلاعات منطبق ثبت می‌شود |
| نتیجهٔ تایید `202` | پرداخت نشده/ناموفق؛ وضعیت از استعلام همان تراکنش خوانده می‌شود |
| وضعیت استعلام `-1` | تراکنش همچنان معلق می‌ماند و سفارش ناموفق یا لغوشده نمی‌شود |
| وضعیت استعلام `3` پس از نتیجهٔ `202` | انصراف مشتری ثبت می‌شود |
| سایر وضعیت‌های ناموفق مستند، از جمله خطا یا برگشت تراکنش | پرداخت موفق تلقی نمی‌شوند |
| وضعیت پرداخت‌شده در استعلام پس از پاسخ تایید `202` | تغییر وضعیت بین دو درخواست؛ تایید باید دوباره انجام شود و نتیجهٔ ناموفق قطعی ثبت نمی‌شود |
| کدهای `102`، `103`، `104`، `115` و `203` یا نتیجهٔ غیرمنتظره | خطای پذیرنده/IP/شناسه یا API؛ سفارش پرداخت‌شده نمی‌شود |

تایید و ثبت نتیجه در تراکنش دیتابیس انجام می‌شود و ترتیب قفل‌ها `Order` سپس `Payment` است. callback موفقِ تکراری دوباره تایید یا اعمال نمی‌شود. تلاش‌های مختلف برای یک سفارش نیز تحت همان قفل سفارش پردازش می‌شوند.

اگر تلاش دیگری برای سفارشِ قبلاً پرداخت‌شده واقعاً وجه دریافت کند، دریافت وجه در رکورد پرداخت حفظ و `needs_refund=True` ثبت می‌شود؛ سفارش دوباره پرداخت یا موجودی دوباره مصرف نمی‌شود. پرداخت واقعی پس از لغو سفارش نیز از روند موجود بازگشت وجه استفاده می‌کند و سفارش لغوشده احیا نمی‌شود. انقضای محلی رکورد پرداخت مانع بررسی موفقیت واقعی دیرهنگام نزد زیبال نیست.

## شبکه، خطا و دادهٔ حساس

قطع اتصال، timeout، خطاهای HTTP، پاسخ ناقص HTTP، JSON نامعتبر، پاسخ ناقص یا اطلاعات مالی نامنطبق به خطای پرداخت کنترل‌شده تبدیل می‌شوند. خطای تایید وضعیت پرداخت را موفق یا شکست قطعی نمی‌کند؛ پردازش همان callback قابل تکرار است. در صورت گم شدن پاسخ تایید پس از تایید واقعی در زیبال، پاسخ `201` و استعلام برای بازیابی استفاده می‌شوند.

API فقط به مقصدهای رسمی فراخوانی می‌شود و redirect پاسخ API دنبال نمی‌شود. URL صفحهٔ پرداخت از شناسهٔ معتبر ساخته می‌شود، بنابراین تغییر `metadata.redirect_url` نمی‌تواند مشتری را به مقصد دیگری بفرستد.

نام پذیرنده از محیط سرور خوانده می‌شود. اطلاعات کارت، credential و متن دلخواه پاسخ API در دادهٔ تایید ذخیره نمی‌شوند. لاگ از پیام‌های کنترل‌شده و کد نتیجه استفاده می‌کند و credential یا بدنهٔ درخواست را چاپ نمی‌کند. ساختار لاگ و استثناهای موجود `PaymentGatewayError` و `PaymentError` حفظ شده است.

## تنظیم محیط توسعه و تولید

| متغیر | مقدار و الزام |
| --- | --- |
| `PAYMENT_GATEWAY` | `zibal`؛ مسیر موجود `payments.gateways.zibal.ZibalGateway` نیز پشتیبانی می‌شود |
| `ZIBAL_MERCHANT` | شناسهٔ واقعی از پنل زیبال در تولید؛ مقدار عمومی `zibal` فقط حساب تست رسمی با `DEBUG=True` |
| `ZIBAL_TIMEOUT_SECONDS` | اختیاری، پیش‌فرض ۱۰ ثانیه؛ باید عدد مثبت و متناهی باشد |
| `SITE_URL` | آدرس عمومی فروشگاه؛ HTTPS در تولید، برای ساخت `/payments/callback/` |

نمونهٔ تولید:

```env
PAYMENT_GATEWAY=zibal
ZIBAL_MERCHANT=
ZIBAL_TIMEOUT_SECONDS=10
SITE_URL=https://minikandoo.ir
```

مقدار خالی `ZIBAL_MERCHANT` را با شناسهٔ پنل پر کنید و آن را فقط در فایل محیط خصوصی یا مدیریت secrets نگه دارید. تنظیمات تولید با پذیرندهٔ خالی یا حساب تست بالا نمی‌آیند. شناسهٔ واقعی در کد، frontend یا Git قرار داده نشده است.

دامنهٔ callback و دامنهٔ آغاز پرداخت باید با سایت ثبت‌شدهٔ پذیرنده مرتبط باشند. در صورت فعال بودن محدودیت IP در پنل، IP خروجی سرور را مجاز کنید. سرور برای درخواست/تایید/استعلام به HTTPS خروجی `gateway.zibal.ir` نیاز دارد. callback روی دامنهٔ فروشگاه ساخته می‌شود؛ میزبان جداگانهٔ `API_URL` که URLconf محدود دارد، برای callback انتخاب نمی‌شود.

فایل‌های Compose متغیرهای جدید را به Django می‌رسانند. شبکه‌ها، سرویس‌ها، volumeها، Dockerfile، Nginx، Gunicorn و Redis تغییر نکرده‌اند.

زیبال هدر `Referer` را برای Start الزامی کرده است. سیاست فقط روی پاسخ، meta و لینک صفحهٔ انتقال پرداخت به `strict-origin-when-cross-origin` تنظیم شده تا origin فروشگاه فرستاده شود. این رفتار در مرورگر با شبیه‌سازی هدر افزودهٔ `same-origin` از Nginx، با و بدون JavaScript، آزمایش شد؛ سیاست عمومی سایت و ظاهر صفحه تغییر نکرده‌اند.

شبیه‌ساز اجرایی قبلی `payments/gateways/mock.py` و صفحهٔ `templates/payments/mock_gateway.html` حذف شدند؛ تابع، مسیر URL و منطق امضای آن‌ها نیز حذف شده است. fixtureهای تست، درگاه دوم نیستند: پاسخ HTTP درگاه زیبال را فقط در محیط موقت آزمایش شبیه‌سازی می‌کنند و مسیرهایشان در URLconf عمومی وجود ندارند.

نمونه‌کدها و ارجاع‌های درگاه قبلی از راهنما، معماری، رابط و registry پاک شدند. SDK یا dependency اجرایی آن در نسخهٔ موجود نصب نشده بود؛ هیچ dependency برنامه افزوده یا جابه‌جا نشده و `pyproject.toml`، `uv.lock`، `package.json` و `package-lock.json` بدون تغییرند.

## آزمون‌ها و ممیزی نهایی

| بررسی | نتیجه |
| --- | --- |
| مجموعهٔ پایه پیش از تغییر | ۲۶۰ تست موفق |
| مجموعهٔ کامل نهایی Django روی SQLite ایزوله | ۳۰۳ تست؛ ۳۰۰ اجرا و موفق، ۳ آزمون قفل ردیفی مطابق قابلیت backend اجرا نشد |
| تمام تست‌های پرداخت روی MariaDB 11.4.13 موقت | ۸۲ تست موفق، بدون skip؛ شامل هر سه آزمون همزمانی |
| مرورگر Chrome / Playwright | ۹ سناریوی موفق: چهار حالت انتقال/Referer، شکست، انصراف/تلاش مجدد، موفقیت بدون JavaScript، callback تکراری و خرید کامل |
| `manage.py check` و URL/importها | بدون خطا |
| `makemigrations --check --dry-run` | هیچ تغییر دیتابیس لازم نیست |
| `manage.py check --deploy` | خروج موفق؛ فقط هشدار موجود `security.W004` برای HSTS صفر |
| رد پیکربندی نامعتبر تولید | پذیرندهٔ خالی، حساب تست و انتخاب درگاه دیگر همگی رد شدند |
| `docker compose ... config --quiet` | پیکربندی توسعه و تولید هر دو معتبر |
| بررسی syntax اسکریپت‌های مرورگر و `git diff --check` | موفق |
| جستجوی ارجاع درگاه قبلی و تنظیمات منسوخ در فایل‌های پروژه | هیچ ارجاع اجرایی یا تنظیم فعالی باقی نمانده |

سه آزمون همزمانی، callback تکراری همزمان، دو پرداخت موفق برای یک سفارش و رقابت پرداخت ناموفق با پرداخت موفق را بررسی می‌کنند. نمونهٔ MariaDB داده و سوکت مستقل در `/tmp` داشت و هیچ پورت شبکه یا اتصال به دیتابیس فروشگاه استفاده نکرد.

اجرای مجموعهٔ ایزوله:

```sh
PYTHONPATH=scripts/qa .venv/bin/python manage.py test --settings=shop_test_settings --noinput
```

برای آزمون مرورگر، Playwright فقط خارج از dependencyهای برنامه نصب شد:

```sh
npm install --prefix /tmp/shop-browser --no-audit --no-fund playwright
PYTHONPATH=scripts/qa .venv/bin/python scripts/qa/setup.py
PYTHONPATH=scripts/qa .venv/bin/python manage.py runserver 127.0.0.1:8765 --settings=shop_qa_settings --noreload
NODE_PATH=/tmp/shop-browser/node_modules node scripts/verify_zibal_browser.cjs
```

## تنظیمات دستی و حدود اعتبارسنجی

برای استفادهٔ واقعی، پذیرندهٔ پنل، دامنهٔ ثبت‌شده و در صورت نیاز IP مجاز باید توسط مسئول استقرار تنظیم شوند. چرخه با credential واقعی یا انتقال وجه واقعی آزمایش نشده است.

اعتبار ساختار Compose بررسی شد، اما build/run کامل کانتینر تولید در این محیط انجام نشد چون Docker daemon در دسترس نبود. هشدار HSTS موجود خارج از محدودهٔ مهاجرت باقی مانده است.

بازگشت وجه برای `needs_refund` طبق روند موجود دستی است. در خطای تایید، شناسهٔ تراکنش را حفظ و همان callback را برای تایید مجدد پردازش کنید؛ پیش از شروع پرداخت تازه در وضعیت مالی مبهم، وضعیت تراکنش موجود باید بررسی شود.

مدل‌ها و migrationها، کد اجرایی سفارش/محصول/سبد/احراز هویت/ارسال/پنل مدیریت، stylesheetها و معماری استقرار در ممیزی diff بدون تغییر تایید شدند.
