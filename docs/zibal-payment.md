# پرداخت زیبال در MiniKandoo

این راهنما رفتار نسخهٔ فعلی را توضیح می‌دهد. اصلاح قبلی پذیرش شمارهٔ مرجع رشته‌ای در commit `910c231f64e2c78677b21699c096e70bbf8756ec` حفظ شده است. راهنمای عملیات در [بازیابی تراکنش‌ها](zibal-verification-recovery.md)، شواهد تراکنش ۷ در [گزارش بررسی دستی](zibal-manual-review-incident.md) و قواعد بکاپ در [بکاپ دیتابیس](production-database-backups.md) قرار دارند. پیاده‌سازی و آزمون محلی، اثبات استقرار یا صحت تراکنش‌های واقعی نیست.

## قرارداد و اعتبارسنجی

چرخهٔ عادی IPG، callback از نوع GET و APIهای JSON روی HTTPS استفاده می‌شوند:

| عملیات | نشانی | نتیجه |
| --- | --- | --- |
| درخواست | `POST https://gateway.zibal.ir/v1/request` | `result=100` فقط ایجاد جلسهٔ پرداخت است |
| ورود مشتری | `https://gateway.zibal.ir/start/{trackId}` | Referer دامنهٔ فروشگاه ارسال می‌شود |
| تأیید | `POST https://gateway.zibal.ir/v1/verify` | `100` نیازمند اطلاعات منطبق و `status=1` است |
| استعلام | `POST https://gateway.zibal.ir/v1/inquiry` | برای بررسی مستقل و بازیابی استفاده می‌شود |

مبلغ از `Order.total` در سرور گرفته می‌شود. ذخیره‌سازی به تومان باقی می‌ماند و adapter برای زیبال آن را در ۱۰ ضرب می‌کند. مبلغ، شمارهٔ سفارش، شناسهٔ تراکنش در صورت وجود در پاسخ، وضعیت و شمارهٔ مرجع تطبیق داده می‌شوند. `trackId` عدد مثبت int64 است و در `Payment.authority` به شکل رشتهٔ یکتا ذخیره می‌شود.

schema و مثال‌های رسمی پاسخ Verify/Inquiry کلید `trackId` ندارند؛ درخواست این APIها با همان شناسهٔ ذخیره‌شده ارسال می‌شود. نبود کلید در پاسخ، اختلاف شناسه نیست. اگر کلید حاضر باشد، عدد صحیح معتبر یا نمایش رشته‌ای همان عدد با `authority` مقایسه می‌شود؛ `null`، boolean، شناسهٔ نامعتبر یا اختلاف واقعی رد می‌شوند. `refNumber` شمارهٔ مرجع مالی دیگری است و نباید به‌جای `trackId` مقایسه شود. فرمان خواندنی `inspect_zibal_payment` وجود کلید، نوع و نتیجهٔ تطبیق را بدون چاپ شناسه‌ها گزارش می‌کند.

`refNumber` یکی از این دو شکل را می‌پذیرد:

- integer مثبت با نمایش حداکثر ۶۴ رقم؛ boolean، حتی `True`، integer معتبر نیست.
- رشتهٔ ۱ تا ۶۴ رقم ASCII مطابق `[0-9]{1,64}` با مقدار مثبت؛ صفرهای ابتدایی عیناً حفظ می‌شوند.

صفر، مقدار منفی، float، علامت مثبت، فاصله، newline، نقطهٔ اعشار، object، رقم فارسی/عربی و مقادیر طولانی رد می‌شوند. دادهٔ خراب به شمارهٔ معتبر تبدیل نمی‌شود. **۶۴ حد موجود `Payment.reference_id` در پروژه است؛ OpenAPI زیبال حداکثر طولی برای `refNumber` اعلام نکرده است.** توصیف رسمی integer است، اما گزارش حادثه نشان داده که پاسخ واقعی می‌تواند numeric string باشد.

پارامترهای callback شامل `trackId`، `success`، `status` و `orderId`، بدون تکرار و با مقدار معتبر، لازم‌اند. تراکنش از شناسهٔ ذخیره‌شده و `gateway=zibal` پیدا می‌شود. `success=1` در URL اثبات پرداخت نیست. پاسخ Verify با کد `201` فقط با Inquiry معتبر پذیرفته می‌شود؛ `202` نیز نیازمند Inquiry است. تغییر به وضعیت پرداخت‌شده بین Verify و Inquiry، خطای قابل تکرار است. خطای شبکه، HTTP، JSON یا اطلاعات مالی، سفارش را موفق نمی‌کند.

## ایجاد پایدار پرداخت و نتیجهٔ نامطمئن

`create_payment_for_order` سه مرحله دارد: ابتدا زیر قفل سفارش eligibility، اقلام، رسید دستی و تلاش‌های قبلی بررسی و یک `Payment` با UUID محلی، مبلغ ثابت و `creation_status=requesting` ثبت می‌شود. `authority` تا دریافت شناسهٔ واقعی زیبال `NULL` است؛ UUID جای track ID گذاشته نمی‌شود. تراکنش commit می‌شود، سپس `/v1/request` بدون قفل سفارش/پرداخت اجرا می‌شود. در پایان تراکنش کوتاه `Order → Payment` وضعیت تازه را می‌خواند و شناسه و نتیجهٔ امن ایجاد را ثبت می‌کند.

UUID در مسیر `callback/<request_id>/` قرار می‌گیرد تا callback زودرس یا پس از timeout به همان تلاش متصل شود. خود مسیر یا `success=1` مجوز اتصال شناسه/fulfillment نیست: ابتدا Verify/Inquiry سروری با مبلغ، سفارش و شناسهٔ منطبق لازم است؛ سپس اتصال زیر قفل انجام می‌شود. callbackهای قدیمیِ `callback/` برای track ID ثبت‌شده همچنان کار می‌کنند. اگر callback زودتر نهایی شود، پاسخ ایجاد، شمارهٔ مرجع، زمان‌ها، تصمیم یا موجودی آن را بازنویسی نمی‌کند.

| وضعیت ایجاد | رفتار |
| --- | --- |
| `requesting` | تلاش قبل از HTTP ثبت شده؛ درخواست همزمان دیگری به درگاه ارسال نمی‌شود |
| `ready` و پرداخت pending | همان session معتبر استفاده می‌شود؛ درخواست تازه ساخته نمی‌شود |
| `uncertain` | timeout، HTTP/JSON خراب یا نتیجهٔ ناشناخته؛ سابقه حفظ و ارسال دوباره ممنوع است |
| `rejected` | رد صریح با کد مستند، بدون شناسهٔ تراکنش؛ تلاش جدید مجاز است و رد قبلی حفظ می‌شود |
| `review` | شناسهٔ متعارض یا سفارش/رزرو/رسید دستی هنگام HTTP تغییر کرده؛ شناسه و audit حفظ و URL تازه به مشتری داده نمی‌شود |

انقضای محلی `Payment` اثبات ناموفق‌بودن session زیبال نیست؛ در صورت eligibility سفارش، session شناخته‌شده دوباره استفاده می‌شود. چند session قدیمی حل‌نشده نیز ایجاد session تازه را متوقف می‌کنند. crash قبل از ثبت پاسخ، تلاش را `requesting` باقی می‌گذارد؛ timeout به معنی ساخته‌نشدن تراکنش در زیبال نیست. در OpenAPI رسمی بررسی‌شده، کلید idempotency برای `/v1/request` و Inquiry با UUID محلی مستند نشده است. UUID فقط هم‌بستگی محلی است و deduplication سمت زیبال را تضمین نمی‌کند.

برای نتیجهٔ نامطمئن، پشتیبانی track ID را از شواهد مستقل زیبال پیدا و طبق [راهنمای recovery](zibal-verification-recovery.md) به تلاش موجود متصل می‌کند. بدون track ID قابل اعتبارسنجی، درخواست خودکار تازه یا پاک‌کردن دستی وضعیت مجاز نیست. وضعیت ایجاد، رسید موفقِ `MANUAL_REVIEW` نیست و به‌تنهایی پرداخت، refund یا نگه‌داشتن رزرو پس از انقضا را اثبات نمی‌کند.

اگر انقضا/لغو هنگام HTTP زودتر commit کند، session ایجادشده حفظ ولی سفارش احیا نمی‌شود. دریافت بعدی وجه طبق قواعد timestamp/refund/manual بررسی می‌شود. صفحهٔ redirect eligibility فعلی و blockers را دوباره بررسی می‌کند؛ لینک قدیمی برای سفارش لغوشده، منقضی یا دارای رسید دستی ارائه نمی‌شود. `ZIBAL_TIMEOUT_SECONDS` مثبت و محدود، timeout اتصال و خواندن socket است؛ هیچ retry خودکار `/v1/request` وجود ندارد.

## شاهد رسمی دربارهٔ paidAt و timezone

منابع در ۲۰۲۶-۱۱-۱۷ دوباره دریافت و بررسی شدند؛ checksum با بررسی قبلی یکسان بود:

- [راهنمای رسمی IPG](https://help.zibal.ir/ipg/)
- [OpenAPI رسمی](https://api.zibal.ir/static/helpdocs/ipg.json)، OpenAPI `3.1.1`، نسخهٔ `1.0.0`
- SHA256 فایل بررسی‌شده: `0231758f40572777e98b12107926363dcf84a9af120c5485b5e3209a9a31a3e2`

در schema پاسخ `/v1/verify` و `/v1/inquiry`، `paidAt` رشته، `format=date-time` و توضیح «به فرمت ISODate» دارد. مثال‌های رسمی `2018-03-25T23:43:01.053000` و `2022-07-06T14:18:21.742000` فاقد offset هستند. منابع عمومی بررسی‌شده timezone این مثال‌ها، UTC یا `Asia/Tehran` را مشخص نمی‌کنند و تأیید کتبی پشتیبانی در اختیار این بررسی نیست. قرارداد توضیح timestamp در هر دو endpoint یکسان است؛ امکان درخواست پاسخ دارای offset یا تنظیم timezone در درخواست این APIها مستند نشده است. parser پاسخ دارای offset را می‌پذیرد، اما آزمون مصنوعی آن تضمین رفتار واقعی API نیست. بنابراین قالب رسمی به‌تنهایی مجوز فرض‌کردن timezone نیست.

`payments/gateways/zibal_time.py` زمان را مستقل تفسیر می‌کند:

| ورودی | تفسیر |
| --- | --- |
| ISO با `Z` یا offset معتبر مثل `+03:30` | با همان offset به UTC تبدیل می‌شود؛ تنظیم محلی آن را جایگزین نمی‌کند |
| ISO بدون offset و تنظیم خالی | `manual_review` با دلیل `timezone_unconfirmed`؛ بدون fulfillment یا تصمیم خودکار refund |
| ISO بدون offset و IANA رسماً تأییدشده | با `ZIBAL_PAID_AT_TIMEZONE` تفسیر و به UTC تبدیل می‌شود |
| timezone نامعتبر، DST fold یا gap | بررسی دستی؛ یک ساعت احتمالی به‌طور دلخواه انتخاب نمی‌شود |
| `-00:00` | offset نامعلوم RFC3339؛ بررسی دستی |
| تاریخ نامعتبر، بیش از ۶ رقم اعشار، offset مثل `+03:60`، زمان خارج از محدودهٔ ذخیره‌سازی | بررسی دستی؛ داده اصلاح یا کوتاه نمی‌شود |
| زمان آینده نسبت به مشاهدهٔ فعلی | بررسی دستی؛ رسیدن ساعت به آن زمان موجب پذیرش خودکار در retry نمی‌شود |

به‌صورت پیش‌فرض:

```env
ZIBAL_PAID_AT_TIMEZONE=
```

پس از تأیید کتبی زیبال، نام IANA تأییدشده را در محیط خصوصی ثبت و منبع و تاریخ تأیید را در پروندهٔ عملیات نگه دارید. تغییر تنظیم کافی است؛ منطق اصلی بازنویسی نمی‌شود. این راهنما مقدار timezone پیشنهادی ندارد. گزینهٔ `--gateway-timezone` در ابزار بازیابی نیز فقط برای همین تأیید رسمی است.

متن پرسش برای پشتیبانی زیبال در [راهنمای بازیابی تراکنش ۷](zibal-verification-recovery.md#تراکنش-۷-سفارش-۳-علت-ثبتشده-و-مسیر-بعدی) آمده است. هیچ پیام یا درخواست پشتیبانی در این کار ارسال نشده است.

## معنای زمان‌های ذخیره‌شده

| فیلد | معنا |
| --- | --- |
| `Payment.gateway_paid_at` | زمان واقعی گزارش‌شده توسط درگاه، پس از تفسیر قابل اتکا؛ nullable است |
| `Payment.paid_at` | زمان محلی اولین ثبت موفق دریافت وجه؛ در retry بازنویسی نمی‌شود |
| `Payment.verified_at` | زمان محلی بررسی سروری |
| `Order.paid_at` | زمان محلی پذیرش پرداخت برای سفارش |

مقایسه با `Order.expires_at` بر اساس `gateway_paid_at` است. زمان ورود callback، زمان پرداخت مشتری محسوب نمی‌شود. raw `paidAt` در `metadata.verification.paidAt` و پاسخ‌های متفاوت در `verification_history` حفظ می‌شوند؛ تفسیر در `metadata.verification.payment_time` و تصمیم در `metadata.decision` قرار دارد. `decision_history` تصمیم قبلی، از جمله تصمیم legacy فاقد تاریخچه، را پیش از ثبت تصمیم تازه حفظ می‌کند. علت‌های تاریخیِ زمان آینده و تعارض رسید نیز پس از تغییر پاسخ مؤثر می‌مانند؛ تأیید timezone مجوز پاک‌کردن آن‌ها نیست. زمان آیندهٔ قابل parse نیز برای ممیزی ذخیره می‌شود، اما وضعیت پرداخت همچنان manual review است. برای legacy records، زمان درگاه از زمان‌های محلی یا مثال مستندات ساخته نمی‌شود.

## مهلت، موجودی و پرداخت اضافه

| وضعیت | رفتار |
| --- | --- |
| پرداخت ۱۰:۲۸، مهلت ۱۰:۳۰، callback ۱۰:۳۵؛ سفارش فعال و رزرو سالم | پرداخت پذیرفته می‌شود؛ رسیدن دیرهنگام callback مانع نیست |
| زمان واقعی پرداخت پس از مهلت | دریافت موفق وجه ثبت، `needs_refund=True`؛ سفارش پرداخت‌شده نمی‌شود؛ job انقضا وضعیت و آزادسازی را انجام می‌دهد |
| job انقضا قبلاً لغو و موجودی را آزاد کرده است | سفارش احیا و موجودی دوباره رزرو نمی‌شود، حتی با زمان زودهنگام معتبر؛ رسید برای refund handling ثبت می‌شود |
| سفارش قبلاً با تراکنش دیگر پرداخت شده | رسید دوم حفظ و refund flag می‌گیرد؛ fulfillment دوباره انجام نمی‌شود |
| timestamp مبهم یا نامعتبر | `manual_review` مستقل؛ بدون fulfillment یا فرض دیرکرد/refund، حتی روی سفارش لغوشده یا پرداخت‌شده |
| سفارش فعال ولی آیتم/واریانت رزرو مفقود است | بررسی دستی و حفظ رسید؛ موجودی اختراع نمی‌شود |

زمان دقیقاً برابر مهلت، داخل مهلت محسوب می‌شود. `Order.inventory_released` آزادسازی رزرو را ثبت می‌کند. آزادسازی تنها یک بار، در مسیر لغو/انقضا، تحت قفل انجام می‌شود. ایجاد سفارش موجودی را رزرو می‌کند؛ callback موجودی را دوباره کاهش نمی‌دهد. وضعیت‌های ناموفق بعدی نمی‌توانند سفارش پرداخت‌شده را تنزل دهند.

اگر رسید موفق دیگری برای همان سفارش `MANUAL_REVIEW` باشد، callback معتبر تازه نیز با دلیل `another_receipt_requires_review` در بررسی دستی ثبت می‌شود؛ زمان قابل‌فهم آن، رسید قبلی را کنار نمی‌زند. شناسه‌ها، raw `paidAt` و تاریخچهٔ Verify حفظ و `needs_refund=False` می‌ماند. پس از paid شدن معتبر سفارش، رفتار پرداخت اضافه و کنترل سفارش لغوشده/رزرو آزادشده همچنان برقرار است.

همین مانع برای شاهد موفق تاریخی در وضعیت غیرنهایی نیز اعمال می‌شود؛ status محلی به‌تنهایی دریافت وجه را نفی نمی‌کند. verification قبلی حتی بدون `paid_at` در تاریخچه حفظ می‌شود و Inquiry ناموفق بعدی آن را پاک نمی‌کند؛ تعارض، بررسی دستی است و پرداخت دیگری از آن عبور نمی‌کند.

سفارش دارای رسید بررسی دستی، حتی پس از مهلت، خودکار منقضی نمی‌شود. query اولیه آن را حذف می‌کند و job پس از قفل سفارش دوباره وضعیت مالی سفارش و وجود رسید دستی را بررسی می‌کند. رزرو صرفاً نگه داشته می‌شود و سفارش paid نمی‌شود. این موجودی ممکن است تا حل پرونده اشغال بماند؛ پشتیبانی باید سریع بررسی کند. اگر آخرین رسید دستی با تصمیم مالی معتبر به refund تبدیل شود، وضعیت بررسی دستی سفارشِ unpaid زیر همان قفل رفع می‌شود؛ خود این کار stock را آزاد نمی‌کند و انقضای عادی بعداً آن را دقیقاً یک بار آزاد می‌کند. پاسخ failed به‌تنهایی این حفاظت را رفع نمی‌کند. پذیرش معتبر رسید از `mark_order_paid` انجام می‌شود.

## وضعیت هماهنگ برای مشتری و ادمین

برای سفارش فعال و unpaid، ثبت رسید `manual_review` زیر قفل `Order → Payment`، `Order.payment_status` را نیز `manual_review` می‌کند. `Order.status` به `paid` تغییر نمی‌کند، `Order.is_paid` همچنان false است و deadline و رزرو حفظ می‌شوند. callback ناموفقِ تلاش قدیمی نمی‌تواند این وضعیت را به pending/failed تنزل دهد.

سفارش‌های قبلی ممکن است هنوز `payment_status=pending` داشته باشند. `with_payment_review()` با `Exists` همهٔ رسیدهای دستی سفارش را برای نمایش بررسی می‌کند؛ به پنج تلاش اخیر محدود نیست. `display_payment_status` و `display_status` نشان دقیق را در رسید، تاریخچه، قالب‌های مکمل و داشبورد می‌دهند. مشاهدهٔ صفحه دادهٔ مالی را تغییر نمی‌دهد. annotation فقط snapshot نمایش است؛ سرویس ایجاد پرداخت، callback و انقضا نسخهٔ تازهٔ سفارش را زیر قفل می‌خوانند.

پیام مشترک مشتری:

> زیبال دریافت وجه را تأیید کرده است، اما سفارش نیازمند بررسی پشتیبانی است. لطفاً پرداخت تازه انجام ندهید و با پشتیبانی تماس بگیرید. آماده‌سازی سفارش پس از پذیرش نهایی پرداخت انجام می‌شود.

دکمه و مسیر POST پرداخت مجدد بسته‌اند؛ URLهای قدیمی موفق/ناموفق/لغو نیز سفارش unpaid دارای رسید دستی را به رسید سفارش هدایت می‌کنند. `payment_callback` برای بررسی دستی warning می‌دهد؛ دریافت موفق درگاه مجوز صفحهٔ موفقیت نهایی نیست. نشان پرداخت هر شش وضعیت `pending/successful/failed/cancelled/expired/manual_review` را دارد. ادمین سفارش و پرداخت همان عنوان «نیازمند بررسی پشتیبانی» را نشان می‌دهند؛ فیلتر و آمار ادمین رکورد legacy را نیز از pending عادی جدا می‌کنند.

سفارش دارای primary پذیرفته‌شده با یک رسید اضافهٔ مبهم به unpaid تنزل نمی‌یابد؛ پیام آن دربارهٔ بررسی یکی از پرداخت‌هاست. مانع پرداخت تازه و حفظ رسید اضافه برقرار می‌مانند.

manual review در پنل مدیریت با فیلتر وضعیت و نمایش زمان درگاه/metadata قابل بررسی است. کاربر پیام مراجعه به پشتیبانی می‌بیند و ایجاد پرداخت تازه برای همان سفارش مسدود می‌شود. `needs_refund=True` صرفاً نیاز به بررسی بازگشت وجه است؛ هیچ refund خودکاری وجود ندارد. تأیید انسانی موارد مبهم باید با ممیزی انجام شود؛ تغییر مستقیم status یا حذف رسید راه حل نیست.

## قفل و ایدمپوتنسی

callback دو مرحله دارد: ابتدا snapshot لازم و هویت callback خوانده و HTTP Verify/Inquiry بدون `transaction.atomic` یا قفل ردیف انجام می‌شود. سپس یک تراکنش کوتاه با ترتیب `Order → Payment → ProductVariant` وضعیت تازه را می‌خواند و idempotency، هویت، primary دیگر، رسیدهای دستی، زمان و موجودی را دوباره بررسی می‌کند. caller نباید سرویس را در یک تراکنش بیرونیِ شامل HTTP قرار دهد؛ view و فرمان recovery مستقیم فراخوانی می‌کنند. لغو/انقضا `Order → ProductVariant` و واریانت‌ها ascending PK را قفل می‌کنند.

مجوز داخلی recovery فقط برای primary مشخص، پس از Inquiry کامل همهٔ رسیدهای بالقوه موفق، زمان‌ها و referenceهای معتبر، انتخاب primary یکتا و بکاپ تازهٔ معتبر صادر می‌شود. boolean یا پارامتر callback نمی‌تواند این مجوز را فعال کند. مجوز به fingerprint کل تاریخچه، شواهد و plan ثبت‌شده در audit متصل است؛ تغییر تاریخچه یا timestamp/reference هنگام HTTP، آن را بی‌اعتبار می‌کند. این مجوز فقط مانع «رسید دستی دیگر» را برای همان primaryِ بررسی‌شده رفع می‌کند؛ cancellation، inventory release، deadline، future time، هویت و قفل‌ها همچنان کنترل می‌شوند.

اگر callback اول قفل سفارش را بگیرد و پرداخت معتبر را بپذیرد، job انقضا پس از گرفتن قفل، paid بودن را دوباره بررسی و از لغو صرف‌نظر می‌کند. اگر انقضا اول قفل بگیرد، لغو و آزادسازی commit می‌شوند و callback بعدی صرفاً رسید و refund/review را ثبت می‌کند. callback پس از موفقیت نهایی، Verify تازه نمی‌زند. دو callback هم‌زمانِ هنوز نهایی‌نشده ممکن است هر دو Verify/Inquiry کنند؛ ثبت نهایی و fulfillment فقط یک بار است و درخواست دیرتر دادهٔ قطعی را بازنویسی نمی‌کند. تلاش‌های مختلف زیر قفل مشترک سفارش فقط یک primary می‌سازند. گذار ادمین به `paid` بدون وضعیت مالی موفق رد می‌شود.

ذخیرهٔ فرم ادمین نیز ابتدا سفارش را قفل و تازه می‌خواند و فقط فیلدهای قابل‌ویرایشِ واقعاً تغییرکرده را می‌نویسد. فرم قدیمی نمی‌تواند `payment_status`، زمان پرداخت یا `inventory_released` ثبت‌شده توسط callback/انقضا را برگرداند. وضعیت ایجاد و UUID در Payment Admin خواندنی و قابل فیلتر/جست‌وجو هستند؛ هیچ action یک‌کلیکی برای موفق‌کردن یا refund اضافه نشده است.

## migration و تنظیمات

migrationهای پایه و migration ایجاد پایدار لازم‌اند:

این اصلاح schema را تغییر نمی‌دهد و `makemigrations --check --dry-run` در تنظیمات ایزوله تغییری پیدا نکرد. طبق گزارش مالک، سه migration زیر قبلاً در production اعمال شده‌اند؛ این وضعیت مستقیماً در production بررسی نشده و اجرای دوبارهٔ migration بخشی از رفع این حادثه نیست.

```text
orders/0002_order_inventory_released_alter_order_payment_status
payments/0003_payment_gateway_paid_at_alter_payment_needs_refund_and_more
payments/0004_payment_creation_status_payment_request_id_and_more
```

اولی سفارش‌های legacy لغوشده را به‌صورت محافظه‌کارانه `inventory_released=True` علامت می‌زند؛ هیچ stock یا وضعیت سفارش تغییر نمی‌کند. دومی فیلد nullable درگاه و choice بررسی دستی را اضافه می‌کند. زمان‌های محلی، مبلغ و reference قبلی حفظ می‌شوند. forward/backward در دیتابیس‌های جداگانه آزمایش شده‌اند. برگشت schema پس از ایجاد سوابق جدید manual review به بررسی جداگانه نیاز دارد؛ migration عقب، ابزار بازیابی داده نیست.

`0004` وضعیت ایجاد و UUID nullable اضافه و authority را nullable می‌کند؛ سوابق قبلی `ready` و بدون UUID ساختگی باقی می‌مانند. reference، مبلغ، metadata و زمان‌های قبلی تغییر نمی‌کنند. برگشت آن فقط برای دیتابیس دارای سوابق legacy ممکن است؛ وجود درخواست جدید/authority نامعلوم، reverse را پیش از حذف فیلدها متوقف می‌کند تا audit از بین نرود. در production با `MIGRATE_ON_START=0`، entrypoint فقط `migrate --check` می‌کند و با migration معوق وب را شروع نمی‌کند؛ اعمال migration همچنان عملیات جداگانهٔ مسئول استقرار است.

تنظیمات اصلی:

```env
PAYMENT_GATEWAY=zibal
ZIBAL_MERCHANT=
ZIBAL_TIMEOUT_SECONDS=10
ZIBAL_PAID_AT_TIMEZONE=
SITE_URL=https://minikandoo.ir
```

merchant واقعی فقط در محیط خصوصی قرار می‌گیرد؛ حساب تست `zibal` در production ممنوع است. endpoint، Referer، URLconf، تبدیل تومان/ریال و سوابق درگاه‌های تاریخی حفظ شده‌اند. whitelist ممیزی شامل داده‌های لازم پرداخت است؛ کارت، merchant، پیام دلخواه gateway و credential در گزارش‌ها ثبت نمی‌شوند.

## تکرار آزمون محلی

```sh
PYTHONPATH=scripts/qa .venv/bin/python manage.py test --settings=shop_test_settings --noinput
PYTHONPATH=scripts/qa .venv/bin/python manage.py makemigrations --check --dry-run --settings=shop_test_settings
.venv/bin/python scripts/qa/test_backup_stack.py
```

دستور آخر کل suite را روی MariaDB جداگانه اجرا و backup image را می‌سازد؛ concurrency، migration و restore را نیز بررسی می‌کند. پاسخ‌های زیبال شبیه‌سازی‌اند. هیچ تست با production settings یا دیتابیس فروشگاه اجرا نشود. روش آزمون و حدود اعتبار در [راهنمای بازیابی](zibal-verification-recovery.md) و نتایج واقعی در گزارش تحویل ثبت می‌شوند.
